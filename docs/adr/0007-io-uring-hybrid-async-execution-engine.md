# Drive io_uring with a three-path hybrid engine over a shared axtask multi-Future executor

PulseOS `io_uring` uses a three-path execution model: an inline non-blocking submission fast path, a shared dual-mode **内核多 Future 执行器** built in `modules/axtask` for native `Future`/`Waker` I/O (reusing the existing end-to-end `axfs` -> `VirtIoBlockFuture` pipeline, `FdObject::register_poll`, and `TimerFuture`), and a globally bounded on-demand kernel worker pool with per-ring round-robin quotas and **异步执行上下文快照** for `IOSQE_ASYNC` and blocking fallbacks. The `io_uring` request state machine and concurrency coordination live in a standalone, host-testable `no_std` core module `modules/pulse_io_uring_core` (paired with the production kernel adapter in `modules/process/src/io_uring/`). The adapter uses the shared `axtask` Future executor.

## Considered Options

- **Pure `FAST_POLL` + `io-wq` worker thread pool:** rejected because sustaining `fio` high `iodepth` would require dozens of stack-backed kernel threads and scheduler switches, leaving PulseOS's existing zero-stack-switch `axfs` -> `VirtIoBlockFuture` async stack unused.
- **One `axtask::spawn_async` task per SQE:** rejected because per-request kernel task allocation, scheduling, and per-CPU GC teardown overhead undermine batched submission gains.
- **Per-ring executor kept private inside `pulse_core` (or one dedicated thread per ring):** rejected because a general multi-Future executor in `modules/axtask` can serve future kernel subsystems as well, and per-ring threads scale poorly for workloads creating many short-lived rings.
- **Allowing synchronous user page faults inside native executor `poll()`:** rejected because `Process::try_fault_in_user_range` may synchronously `block_on` file-backed faults, stalling unrelated in-flight Futures sharing the same executor driver thread.

## Consequences

- **Dual-mode liveness.** By default the executor polls each new native Future once inline, so hardware requests such as VirtIO block descriptors can be submitted immediately. Completion waiters can poll ready Futures cooperatively. A lazy pool of `1..=min(cpu_count, 4)` background drivers also makes progress when the caller submits with `min_complete == 0` or waits in `epoll_wait(ring_fd)`.
- **Reserved CPU placement.** When an SQPOLL ring explicitly selects a reserved service CPU, all its native Futures enter that CPU's ready queue, including newly activated link and drain successors. Each selected CPU has one shared driver bound before its first dispatch. It performs every poll and sleeps when the queue is empty. A wake from another CPU or an IRQ publishes readiness to the same queue.
- **Blocking workers on a reserved CPU.** The global pool claims Path 3 jobs under the same round-robin, ring quota and serial-key rules for all rings. A worker migrates to the ring's selected service CPU before starting the job, keeps its affinity across sleeps, and restores its normal kernel affinity after completion. Other worker stacks can execute on that CPU while it sleeps. For shared file offsets, the pool reserves the position ticket at enqueue and admits ticket holders in reservation order across rings.
- **Non-blocking `poll` discipline:** Futures hosted on the shared `axtask` executor must not call synchronous `block_on`; requests carrying `IOSQE_ASYNC`, non-fixed transfers exceeding the submission-time pinning window that require mid-I/O `try_fault_in_user_range`, or blocking-only descriptors route to the bounded worker pool instead.
- **Three-layer lock hierarchy and drop safety:** IRQ-safe `SpinNoIrq` sections are restricted to CQ/overflow publication, ready-queue handoff, and wakeup notification; `Future::poll`, external `FdObject` calls, and dropping the last `Arc<FileObject>` (whose `File::drop` may call `block_on` for deferred timestamp publication) must always occur outside `SpinNoIrq` and IRQ context, obeying `ring_submit_lock (sleepable)` -> `Process` -> `FdObject/axfs/axnet` -> `ring_completion_ready_lock (SpinNoIrq)` -> `WaitQueue (SpinNoIrq)`.
- **Module extension boundaries:** `modules/axmm` remains unchanged (preserving ADR-0001 and ADR-0004); `modules/axfs` remains non-breaking (exposing existing async entry points through `process::fd::FileObject`); `modules/axnet` / `process::socket` receive only two targeted additions—side-effect-free per-call non-blocking try-ops (replacing racy `TemporaryNonblocking` mutation) and per-socket `register_poll` over existing `axpoll::Pollable` queues (eliminating global `NET_WAIT_QUEUE` thundering herd).
- **Special FD & credential isolation:** Workers execute exclusively against the captured **异步执行上下文快照** (`Arc<Process>`, `Arc<Credentials>`, cloned `axfs::FsContext`) and never fall back to `current_process()`; `EpollObject` and `SignalFdObject` must not be dispatched raw onto pure kernel worker threads where they fail with `ESRCH`.
- **Two-tier verification:** Concurrency state machines are host-tested via `cargo test -p axtask --features "test multitask"` and `cargo test -p pulse_io_uring_core`; end-to-end dual-architecture SMP behavior and overlap gains are verified on RV64 and LA64 QEMU with LTP `io_uring01`–`io_uring04`, `liburing-2.9`, and `fio-3.39 --ioengine=io_uring`.
